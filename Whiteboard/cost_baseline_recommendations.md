# The Signal: Cost Baseline & value_rating Derivation

*Drafted S76 (agy). Rewritten S143 (Claude/Andy) — the original verb-multiplier model was tested against real card data and rejected; this version reflects what actually held up.*

## Goal

Everything in this document is in service of one thing: assigning **`value_rating`** (1–4) to every CA/PA/ModReact card — a floor-to-ceiling power tier (1 = basic/floor action, 4 = end-game-power card), consistent across the whole set. The pricing/UVM work isn't the deliverable; it's the evidence base for that tier assignment.

---

## 1. What agy originally proposed (S76) — superseded

The original model: `recommended_effective_cost = Base Subject Value × Function Multiplier × Certainty Tax`, with a fixed verb-multiplier table (Add=1.0x, Remove=1.5x, Redirect=2.5x, Protect=0.75x) applied to a single per-Subject baseline (PresenceToken=2.0, from Town Hall).

**Tested against real data (S143) and rejected.** Comparing the same Subject under different Functions with n≥2 samples each, the Remove/Add ratio ranges from **1.15x (StructureBlock) to 8.58x (NativeResource)** — no universal multiplier fits any subject consistently. Verb "premium" is subject-specific, not a fixed ratio you can apply generically.

## 2. What replaced it: pair-based pricing

Instead of decomposing cost into `subject-value × verb-multiplier`, treat **(Subject, Function) as one atomic priced unit**, calibrated directly from real card data:

- **`uvm_assumptions`** — per-Subject baseline (28 Subjects, tiered `validated`/`single_example`/`fallback_avg` by sample size). Used as a fallback when a specific pair has no data.
- **`uvm_pair_assumptions`** — 58 real `(subject, function)` pairs, per-unit normalized (divides by magnitude — critical fix, since raw averaging silently blended 1-unit and 2-unit cards together).
- **`v_card_pair_uvm_cost`** — the working view. Infers a verb per effect row (magnitude sign for delta-style effects; `Shift` always for StandingMarker, which has no Add/Remove convention; the card's own declared Function when there's no clean per-row signal), dedupes to distinct pairs per card, sums each pair's calibrated value × its actual magnitude, folds in `successcrit` at a flat 5% weight (crit-success is an unconditional floor per Pillar 4.8b, not conditional on threshold), excludes `failcrit` entirely (mutually exclusive with success — this view specifically answers "what does success cost").
- **Key columns:** `total_pair_cost` (model's estimate of the card's raw worth), `delta_vs_current_cost` (as a **percentage**: `(total_pair_cost − current_effective_cost) / total_pair_cost × 100` — normalizes miss-magnitude by scale, so outliers are comparable across cheap and expensive cards), `has_boost`, `has_multipliers`, `n_fallback_to_subject_only`.

**Current fit:** 129 paid cards (72 `cost=None` cards excluded from the percentage metric — dividing by their own zero cost always shows a trivial +100%, not a real signal). Of the 129: 34 within ±10% (well-calibrated), 30 at 10–30%, 34 at 30–60%, **31 genuine outliers over 60%** — these are the redesign candidates below.

## 4. Open modeling gaps (not card redesigns — the pricing model itself needs more work)

- **Self-cost vs. delivered-value confusion.** `NET.CA.6` Sacrifice correctly pays its cost via `faction(acting).standing -= 2` in the success field (PS isn't a valid `cost`-field value per schema convention — this is right). But the pricing model has no way to distinguish "the acting faction sacrificing their own Standing as payment" from "inflicting Standing loss on an opponent as a delivered effect" — both look like the same mutation, and the model currently prices the self-sacrifice as if it were a benefit. Needs a fix (likely: any success-tier mutation targeting the *acting* faction's own resource downward should subtract from total_pair_cost, or be treated as additional cost, not added value) before the model can be trusted on cards using this pattern.
- **`PublicAct/Modify` scope-granularity concern (S143) — resolved as a non-issue (S144).** Suspected a persistent/one-shot scope conflation; re-audit found the premise was wrong (see §3, the 5-cluster resolution) — the actual driver was 3 unrelated per-card blockers, not a genuine scope-resolution gap in the pricing model. No fix needed; `(Subject, Function)` granularity held up fine once the real cards were traced individually.
- **Second confirmed instance of the self-cost/delivered-value gap (SYN.PA.1, S144), mirror direction.** The gap above (NET.CA.6) was the acting faction's own resource *loss* counted as value. Here it's the opposite: `on_accept`'s `faction(target).standing += 1` — the *opponent's* consolation gain for accepting — gets summed into `total_pair_cost` as if it were value delivered to the acting faction (2 StandingMarker/Shift units counted instead of 1, since both sides' +1 land in the same bucket).
- **Attempted fix (S144), reverted — `target` field semantics are inconsistent across the corpus, not a quick formula fix.** Tried excluding rows where `target='acting'` + negative magnitude (self-cost) or `target IN ('target','other')` + positive magnitude (opponent-benefit) from the value sum. Correctly zeroed out NET.CA.6 (now-empty total_pair_cost — that card delivers no measurable acting-faction value per its own effect rows, a separate finding worth a look) and fixed SYN.PA.1's double-count. **But it also incorrectly zeroed STD.CA.15's entire value** (`total_pair_cost` 1.75→0, already verified correct and just repriced this session/L281): its row is tagged `target='other'` because the expression references `faction(target).supply` as the *source* of the draw, even though the acting faction is the actual beneficiary (`transfer(faction(acting).case)`). So `target` sometimes means "who benefits" and sometimes means "whose game-state the expression reads from" — the same value can't be interpreted consistently without also knowing each category's semantic direction. **Reverted the view to its original definition; no live change.** A real fix needs an audit of what `target` should mean per category (or a new column altogether), not a formula tweak — bigger scope than today's session. Still logging the 2 known-real instances (NET.CA.6, SYN.PA.1) as cards to hand-check manually if their pricing ever needs to be trusted.
- **New: NULL-magnitude fallback misattributes unrelated effect rows onto the card's single declared (subject, function) pair.** `v_card_pair_uvm_cost`'s subquery `dp`: when an effect row's magnitude is NULL (declared-variable effects like `n`, common on ElectPlayer/scaling cards), it assigns that row the card's own single declared `subject`/`function` — correct when the row genuinely matches that pair, wrong when it doesn't. Confirmed on SYN.PA.1: the row `faction(target).resource(capital) += (2*n)` (a Capital payment, unrelated to the card's `PresenceToken/Redirect` tag) gets folded into the `PresenceToken/Redirect` weighted-unit count anyway, inflating it from 2 real units to 3. Any card with ≥2 distinct-subject effects where more than one has a variable/unparseable magnitude is at risk of this same miscount — likely affects other ElectPlayer/scaling cards beyond this one, not yet surveyed.
- **`has_boost` cards are floor-only, not "wrong" — the model literally cannot see N.** Confirmed on GUI.PA.9 and SYN.CA.9 (S144): any effect built on a `count(...)` board-state read (as opposed to a literal magnitude) gets weighted as exactly 1 unit — the absolute floor, not an average or realistic case. This isn't miscounting an existing number (like the two bugs above); there's no number to read at query time at all. `n_distinct_pairs`/`total_pair_cost` for these cards should be read as "value at N=1," full stop — never compared directly to `current_effective_cost` as if it were a real delta. Hand-computing at a plausible realistic N (informed by the card's own restriction/design intent — see the two S144 checklist entries above for worked examples) is the only way to get a usable number today; no automated fix proposed.
- **Confirmed real instance of Add-vs-Redirect mis-tagging (SYN.CA.9, S144, PM02 L278) — worth a light sweep.** Per Art 04b §4's Function table, `Redirect` (not `Add`) is the correct tag for any cross-faction transfer (target loses, acting faction gains, in one operation) — `Add` is defined strictly as bringing a *new* element from supply. SYN.CA.9 was mis-tagged `Add`; SYN.PA.1 already had the correct `Redirect` tag for the same effect shape. Not surveyed further this session — worth checking other `Territory/Add/PresenceToken`(or `StructureBlock`) cards for the same mis-tag, since it affects both taxonomy accuracy and this pricing model's pair-rate lookup.

## 5. Next step toward actual `value_rating` assignment

Once the redesign needs above are addressed (or at least acknowledged as known-soft), the natural next move is bucketing `total_pair_cost` (or a redesign-corrected version of it) into 4 tiers — floor/basic through end-game ceiling. Tier boundaries not yet proposed; that's a design call once the outlier list above stops moving.
